# Harnesses, not models, make app builders work

Public records from Lovable, Vercel v0 and bolt.new tell the same story: the base LLM is a swappable part, and the product lives in the harness around it. That harness is a tool-calling loop with cheap read-only helpers, a context pipeline tuned for prompt-cache hits, a validated line-range edit format, deterministic repair of imports, icons and dependencies while and after the model streams, live preview telemetry fed back to the agent, and a backend control plane that gates every schema change and never lets the agent read secrets. Vercel's clearest data point supports this: its composite `v0-1.5-md` pipeline on Sonnet 4 produced error-free generations **93.87%** of the time, against **78.43%** for raw Claude 4 Opus, and the smaller composite beat the larger `v0-1.5-lg` ([Vercel](https://vercel.com/blog/v0-composite-model-family)). That matters for a LAN clone running Qwen-class models, because most of what separates the commercial products from a raw LLM is deterministic engineering that runs fine on local hardware. On infrastructure, the three vendors split sharply. Lovable runs ephemeral server-side dev servers (Fly.io, then Modal, now moving to a Rust Vite replacement called OJ). v0 moved from an in-browser Next.js emulator to Firecracker microVMs with filesystem-only persistence. bolt.new still runs everything in the user's browser via WebContainers. None of them rolls back database state when a user restores an old version, so this is the one place a self-hosted clone can beat the market cheaply. The recommended blueprint is Lovable's agent loop, edit tool and migration approval flow, plus v0's streaming and post-stream fixers and its docs-as-files context strategy, plus Vercel Sandbox's persistence model mapped onto `podman stop/start`, with one git commit per AI turn and opt-in database snapshots.

## Both vendors wrap a replaceable model in a routing and repair harness

Lovable's builder is Claude-first. Claude 3.5 Sonnet was "the first model that made agents work", and Opus 4.5 through Opus 5.5 followed as defaults. The architecture is described as "a harness around a main agent that can use subagents to orchestrate tasks effectively, with the right models at each step" ([Claude customer story](https://claude.com/customers/lovable)). In August 2026 Lovable publicly dropped the model picker. It now describes a control plane that "assign[s] different parts of the build to different models". It trains **proprietary small models for narrow jobs** (routing requests, summarizing responses, writing commit messages), and it measures whole-app outcomes rather than per-response latency, because "a model can respond quickly and still be slow if it takes three times as many rounds to finish" ([Lovable](https://lovable.dev/blog/the-model-picker-is-a-dead-end)). Its recovery principle is worth copying word for word: "Recovery should change the thing that failed, whether that is the context, plan, tool, or model". Lovable also discourages switching models mid-build because context gets lost. Subagents are parallel and read-only, with isolated context windows, and are used for codebase exploration and web research. "Lighter work gets routed to faster, cheaper models", and "the one thing they can't do is change your code" ([Lovable](https://lovable.dev/blog/subagents-in-lovable)). At the infrastructure layer, Lovable routes more than **1B tokens per minute** across Anthropic, Vertex and Bedrock. It pins each project to one provider because "prompt caching relies on consecutive requests being sent to the same provider" ([Lovable](https://lovable.dev/blog/routing-billions-of-tokens-per-minute)).

The loop itself arrived in mid-2025. Before that, Lovable "tr[ied] to do everything in one single step": it emitted one XML response with whole-file `<lov-write>` blocks. Agent Mode added codebase search, on-demand file reads, log and network inspection, web search and image generation, and Lovable claimed roughly **90% fewer build errors** ([Lovable](https://lovable.dev/blog/agent-mode-beta)), later 91% on complex tasks at GA ([Lovable](https://lovable.dev/blog/agent)). Today there are three modes. Build implements and verifies. Plan investigates and produces an editable plan that the user approves. Chat discusses without touching code. Messages the user sends mid-run are picked up "at its next natural stopping point" ([Lovable docs](https://docs.lovable.dev/features/agent-mode)). The internals are an event-sourced design. Every conversation is a trajectory of events (UserMessage, tool events, IterationEnd, AgentDone) with git-like parent pointers, so forking costs nothing. Each agent has an inbox that is only drained at iteration boundaries, and "context is always assembled from the trajectory" by walking backwards, which gives each agent type its own prompt ([Lovable](https://lovable.dev/blog/how-lovable-agents-work-together)). The leaked September 2025 tool list is unofficial but consistent with the blog. It contains roughly 20 tools: `lov-view`, `lov-search-files`, `lov-line-replace`, `lov-write`, rename/delete/copy, `lov-add-dependency` (package.json is not directly editable), console and network log readers, web fetch and search, image generation, secrets, security scan and Supabase docs search ([leaked Agent Tools.json](https://raw.githubusercontent.com/x1xhlol/system-prompts-and-models-of-ai-tools/main/Lovable/Agent%20Tools.json)).

v0 took the opposite route to the same place. Its June 2025 "composite model" was a Sonnet 3.7 or Sonnet 4 base wrapped in four parts: a RAG step (docs, UI examples, user sources, internal Vercel knowledge), a Quick Edit path for narrow changes, a custom fixer model `vercel-autofixer-01` trained with reinforcement fine-tuning on Fireworks, and deterministic stream rewriting ([Vercel](https://vercel.com/blog/v0-composite-model-family)). In August 2025 v0.dev became v0.app, a tool-calling agent with web search, site screenshots, planning and task tracking ([Vercel](https://vercel.com/blog/v0-app)). Since the August 2026 v2 API, the agent streams typed parts ("text, thinking, file reads and edits, searches, bash commands, tool calls, and agent actions"). It can also load up to three Skills per request, where a skill packages a design system's components, tokens and starter app ([Vercel](https://vercel.com/blog/introducing-the-new-v0-api)). Neither vendor publishes loop termination rules, maximum iteration counts or compaction thresholds.

The two vendors diverge on context. Lovable pre-injects a `useful-context` block and a `current-code` block, and tells the agent to check them "FIRST" before searching. Files not in context must be read before they are written ([leaked Agent Prompt](https://raw.githubusercontent.com/x1xhlol/system-prompts-and-models-of-ai-tools/main/Lovable/Agent%20Prompt.txt)). It also injects fixes from a curated "Lovable Stack Overflow" through a classifier, selector and synthesizer chain, which cut stuck rates by **5%** and raised publish rates by 2% ([Lovable](https://lovable.dev/blog/we-gave-our-agent-a-vent-tool)). v0 uses "embeddings and keyword matching" to detect intent and inject version-specific SDK docs into a system prompt kept deliberately "consistent" to "maximize prompt-cache hits". It explicitly chose this over web search. It also mounts **hand-curated example code as a read-only filesystem** that the agent greps ([Vercel](https://vercel.com/blog/how-we-made-v0-an-effective-coding-agent)). Neither vendor has published anything showing embedding-based RAG over user code. The public evidence points to regex search plus ranged reads.

**Copy for the clone:** use a single strong model (Qwen ~30B-class) for the builder, and a 7–14B model for read-only exploration subagents, commit messages, conversation summaries and a stuck-detector. Read-only mode is simply the builder with write tools withheld. Store the conversation as an append-only event log with iteration boundaries, which gives you resumability and mid-run user messages almost for free. Pin each project to a single vLLM/SGLang replica to keep prefix caches warm, the local version of Lovable's provider affinity. Borrow v0's context strategy wholesale: keep the system prompt byte-stable, put stack docs and shadcn/Supabase examples in a read-only `/docs` mount the agent greps, and auto-inject only `index.css`, `tailwind.config.ts`, the router/`App.tsx` and recently edited files.

## Validated line edits plus deterministic fixers beat bigger models

Lovable's editing protocol went through three phases. First it rewrote whole files. Then it wrote files with `// ... keep existing code` placeholders, which only work if something merges them into the original. Its 2025 primary tool is `lov-line-replace`, which takes a file path, a search block, the first and last line numbers of the replaced range, and the replacement. For spans longer than about 6 lines, the search block is the first 2–3 lines, a `...` line, and the last 2–3 lines. The tool "will validate that search matches the content at the specified line range". Parallel edits to the same file must all use **original** line numbers. Full-file `lov-write` is reserved for new files or as a fallback ([leaked Agent Tools.json](https://raw.githubusercontent.com/x1xhlol/system-prompts-and-models-of-ai-tools/main/Lovable/Agent%20Tools.json)). Nothing public confirms whether Lovable uses a fast-apply model (Morph, Relace) to merge placeholder writes. v0's current edit format is also undocumented beyond "file reads and edits" being tool calls ([Vercel](https://vercel.com/blog/introducing-the-new-v0-api)).

v0 has published its repair stack in detail, and it is the most portable material in this whole survey. "LLM Suspense" rewrites text while it streams. It swaps long blob URLs for short aliases before the model call and restores them afterwards, which also saves tokens. It normalizes import formatting. It checks every lucide-react icon name against the package's real exports, and if the icon doesn't exist it does a vector search for the nearest real one and rewrites the import mid-stream (`VercelLogo` → `Triangle as VercelLogo`), "within 100 milliseconds and requires no further model calls". After the stream, autofixers run AST checks (for example, is `useQuery` wrapped in a `QueryClientProvider`?), deterministically complete `package.json` from the generated imports, and repair common JSX/TS errors in **under 250 ms**. Vercel's framing is that LLM code "can have errors as often as 10% of the time" and that the pipeline gives "a double-digit increase in success rates" ([Vercel](https://vercel.com/blog/how-we-made-v0-an-effective-coding-agent)). The trained fixer ran at **8,130 chars/sec with 86.14% error-free output**, compared with Gemini 2.5 Flash at 559 chars/sec and 89.55% ([Vercel](https://vercel.com/blog/v0-composite-model-family)). In other words, Vercel accepted a small quality loss for a 15x speedup.

Runtime error recovery works in three layers. First, the agent has tools to read preview console logs and network requests, and the prompt tells it to read them *before* reading code when debugging ([leaked Agent Prompt](https://raw.githubusercontent.com/x1xhlol/system-prompts-and-models-of-ai-tools/main/Lovable/Agent%20Prompt.txt)). Lovable's current Build mode "inspect[s] logs, runtime output, and network activity and iterate[s] on fixes". Heavier verification (browser tests, frontend tests, edge-function calls) runs only on request ([Lovable docs](https://docs.lovable.dev/features/agent-mode)). Browser testing uses a remote headless browser that can click, fill forms, resize viewports and "detect runtime errors while interacting" ([Lovable docs](https://docs.lovable.dev/features/browser-testing)). Second, v0's API agent "verifies the code running in the Sandbox, so it can catch and fix errors in your app in real time" ([Vercel](https://vercel.com/blog/introducing-the-new-v0-api)). Third, Lovable runs a meta-loop over the whole system. LLM judges flag stuck users (users who get stuck early are **4x** more likely to churn), and the agent itself has a "vent" tool that posts complaints to Slack, which a debug agent turns into PRs. Roughly 20% of vents led to mergeable fixes, about 10 fixes merge per day, and agents became "less likely to get stuck in long loops of futile re-attempts" ([Lovable](https://lovable.dev/blog/we-gave-our-agent-a-vent-tool)).

**Copy for the clone:** make Lovable's `line-replace` (validated range plus ellipsis search) the primary edit tool. It is deterministic, cheap in output tokens, and it fails loudly instead of silently corrupting a file, which matters more with a 30B model than with Opus. Apply parallel edits bottom-up by original line numbers. Skip placeholder-merge writes unless you want to run a fast-apply model. Build v0's fixers as a plain post-edit pass: resolve every import against `node_modules` and the shadcn component list, fuzzy-match lucide icons (a sorted name list with edit distance is enough; you don't need a vector DB for about 1,500 names), auto-add missing npm dependencies, then run `tsc --noEmit` and a Vite build and feed the errors back as a tool result. Put a hard cap on fix iterations. Following Lovable's recovery principle, when the cap is hit, change something (re-plan, reset context, or escalate to a larger model) instead of retrying the same thing. Log a "vent" tool's output to a local file. It is the cheapest harness-debugging signal you will ever get.

## Previews moved server-side everywhere except bolt.new

Lovable's history is a migration away from owning orchestration. In March 2025 it ran more than **4,000 ephemeral dev servers on Fly.io**, each an isolated Node environment ([Lovable](https://lovable.dev/blog/visual-edits)). It had also built a Kubernetes/AWS orchestrator of about 15,000 lines. It then moved every generation session to **Modal Sandboxes** reached through encrypted Tunnels, cut orchestration code to about **700 lines**, and peaked at **20,000 concurrent sandboxes** during a 250k-app weekend ([Modal](https://modal.com/blog/lovable-case-study)). In September 2026 it announced OJ, a single Rust binary built on Rolldown and Oxc that reads Vite config and bridges Vite plugins. OJ cold-starts a 10k-component app in 1.2 s instead of 4.9 s, uses about **115 MB instead of more than 1.5 GB**, and cut production median preview load from 17.4 s to 8.0 s and sandbox acquisition from 14.5 s to 3.0 s across roughly 1M sandboxes a day ([Lovable](https://lovable.dev/blog/faster-previews-oj)). Lovable publicly documents runtime log capture only through its remote browser. It has not described any in-iframe log bridge.

v0 started with "next-lite", an in-iframe Next.js emulator. It forwarded console events to the parent over a `postMessage`/`MessageChannel` handshake, with timestamps and an `isServer` flag. Vercel states that "API v2 uses VM-backed previews and does not expose console output through this next-lite channel" ([v0 docs](https://v0.app/docs/api/v1/guides/capturing-preview-console-logs)). Users complained that the agent could no longer self-debug from console output ([Vercel community](https://community.vercel.com/t/v0-forced-new-tab-preview-prevents-console-log-access-and-agent-debugging/33597)). The lesson is that the log bridge has to be built on purpose. The new previews run in Vercel Sandbox, where each sandbox is a Firecracker microVM ([Vercel](https://vercel.com/changelog/vercel-sandboxes-ga)). The lifecycle model maps closely onto podman. A sandbox has a stable name per project, and on stop its **filesystem is snapshotted but processes are not**, so the next call resumes the filesystem and the dev server must be relaunched as a detached command whose logs are streamed ([Vercel docs](https://vercel.com/docs/sandbox/concepts)). Defaults are a 5-minute idle timeout and 2 vCPU/4 GB, and snapshots expire after 30 days ([Vercel docs](https://vercel.com/docs/sandbox/pricing)). Community threads suggest that dependency install on resume is the main failure mode ([Vercel community](https://community.vercel.com/t/v0-preview-fails-with-sh-line-1-next-command-not-found-error-in-sandbox/36324?page=2)). bolt.new still runs the dev server in the user's browser via StackBlitz WebContainers, and Bolt Cloud only adds server-side hosting and a database ([taskade review](https://www.taskade.com/blog/bolt-review)). That design suits a public SaaS that wants near-zero preview cost. It is the wrong fit for a LAN product that wants native binaries, Bun and full Linux compatibility.

The reference routing pattern comes from Fly's blueprint for per-user machines. A router steers requests to the right machine, starts it if it's stopped, and keeps a management port (code changes, health checks) separate from the public preview port ([Fly.io docs](https://docs.fly.io/blueprints/connecting-to-user-machines/)). open-lovable skips a custom proxy entirely: it points the iframe at the sandbox provider's URL for Vite on port 5173 ([GitHub](https://github.com/firecrawl/open-lovable)).

**Copy for the clone:** run one rootless podman container per project, stopped when idle and started on demand, with an entrypoint that runs the package install idempotently and then relaunches Vite. That reproduces Vercel's persistence semantics without snapshots. Put a single reverse proxy (Caddy, or a small Bun proxy) in front, mapping `p-<id>.preview.lan` to the container. On a miss it runs `podman start` and holds the request until Vite answers, and it must pass through WebSocket upgrades for HMR (set Vite's `server.hmr.clientPort` and `allowedHosts`). Do file writes and exec through the podman API, never through the preview port. Build the log bridge on day one: a dev-only Vite plugin injects a script that forwards console calls, `window.onerror`, unhandled rejections and failed fetches to the parent frame, and the dev server's stdout streams back to the agent alongside it. Add Playwright only when you want Lovable-style interactive browser testing. Vercel and E2B use Firecracker because the code is untrusted. On a trusted LAN, rootless podman is adequate, but if tenants don't trust each other, switch the OCI runtime to gVisor or Kata. Watch OJ: Lovable's figures say stock Vite's memory, not CPU, is what limits density.

## Every vendor restores code and leaves the database alone

All three create a version automatically on every AI turn. Lovable says "there is no save button". Reverting "is not destructive to your chat", later edits "stay in the project chat, so you can reapply them anytime", and each version can be bookmarked, previewed in a new tab, diffed or opened as a read-only snapshot ([Lovable docs](https://docs.lovable.dev/features/projects/history)). v0 spells out append semantics: "Restoring an old version creates a new, most recent version using the restored code to maintain a linear version history". Manual edits do not create versions ([v0 docs](https://v0.app/docs/versions)). Bolt offers preview, rename, bookmark and restore on a timeline ([Bolt support](https://support.bolt.new/building/using-bolt/rollback-backup)). On data, all three give the same answer. Lovable: "Reverting restores your project's **code only**, and redeploys your app's edge functions to match. It does not restore or roll back your database data" ([Lovable docs](https://docs.lovable.dev/features/projects/history)). Bolt: restoring "will not change your current Bolt or Supabase databases" ([Bolt support](https://support.bolt.new/building/using-bolt/rollback-backup)). Nobody documents an automatic "revert to last working build" either.

**Copy for the clone:** commit once per AI turn in the hidden repo, with the commit message written by the small model. Implement restore as `git checkout <sha> -- .` followed by a new commit ("Restored to vN"), never `reset --hard`. Store bookmarks as lightweight tags. After restoring, redeploy functions from the restored tree, as Lovable does. Then go one step further than the market. Take a `pg_dump` (or a Postgres template-database copy, which is faster for small dev databases) whenever a turn applies a migration, record the dump's ID against the commit, and offer "also restore data" as an explicit opt-in next to the standard code-only warning. Because every schema change already goes through an approval gate (next section), you already know exactly which turns touched the database, so snapshots only happen where they're needed.

## The backend control plane gates migrations and hides secrets

Lovable Cloud (September 2025) is managed Supabase behind Lovable's own UI. It covers database, users, storage, edge functions, jobs, logs and security checks. Schema changes go "via SQL migrations" and regenerate types ([Lovable docs](https://docs.lovable.dev/features/cloud)). The migration flow is the key UX pattern. "Lovable writes the SQL, shows it to you, and asks for your approval in the project chat before running it", then commits it under `supabase/migrations/` and regenerates TypeScript types. When a function deploy fails, the agent reads the function logs. Secrets are entered through a secure input and "Lovable does not read stored secret values back" ([Lovable docs](https://docs.lovable.dev/integrations/supabase)). If a user pastes an API key into chat, Lovable detects it and moves the logic server-side ([Lovable docs](https://docs.lovable.dev/features/security)). v0 contributes the better introspection tool. `GetOrRequestIntegration` returns connection status, env var names, **live schema and RLS policies**, and the prompt tells the agent to use it "instead of reading scripts from files" ([leaked v0 Prompt](https://github.com/x1xhlol/system-prompts-and-models-of-ai-tools/blob/main/v0%20Prompts%20and%20Tools/Prompt.txt)). Integration tools can be set to Disabled, Ask for Approval or Always Run ([v0 docs](https://v0.app/docs/llms.txt)). Bolt's managed database auto-pauses unpublished projects after about 6 days of low use ([Bolt support](https://support.bolt.new/cloud/database)), which is the same scale-to-zero instinct your podman design needs.

Security scanning exists because of **CVE-2025-48757 (CVSS 9.3)**. Of 1,645 Lovable apps sampled, 170 exposed 303 endpoints readable or writable with the public anon key, because RLS was missing or wrong. Lovable's first scanner only "checks for the existence of any RLS policy, not its correctness" ([Matt Palmer](https://mattpalmer.io/posts/statement-on-CVE-2025-48757/)). Today there is a Quick scan before publish (RLS gaps, overly permissive rules, npm vulnerabilities, exposed MCP servers) and an on-demand Deep scan (authorization, abusable endpoints, injection including AI prompts, leaked secrets, payment tampering, auth bypass), with auto-fix for eligible findings ([Lovable docs](https://docs.lovable.dev/features/security)). The root cause is architectural and your stack inherits it. When the browser talks to PostgREST with the anon key, RLS is the only authorization layer.

The self-hosted subset is practical. Upstream compose now uses **Envoy as the default gateway** (Kong is opt-in). The gateway routes `/functions/v1/*` to `functions:9000` with the prefix stripped, and it no longer serves the PostgREST OpenAPI schema to the anon key, which was labelled a security fix ([supabase CHANGELOG](https://github.com/supabase/supabase/blob/master/docker/CHANGELOG.md)). supabase-js calls `${SUPABASE_URL}/functions/v1/<name>` (POST by default) with `Authorization: Bearer <jwt>` and `apikey` headers ([functions-js](https://github.com/supabase/supabase-js/blob/master/packages/core/functions-js/src/FunctionsClient.ts)). That means a Bun server on :9000 that dispatches `/<name>` to `functions/<name>/index.ts` works as a drop-in replacement at the protocol level. It must reimplement JWT verification (edge-runtime's `VERIFY_JWT` is global, and per-function config is still a TODO upstream), CORS preflight, `SUPABASE_*` env injection and some form of per-function isolation ([docker-compose.yml](https://github.com/supabase/supabase/blob/master/docker/docker-compose.yml)). Nobody has publicly shown that Bun-as-edge-runtime works in practice. The compose file already carries podman-specific fixes and needs podman-compose ≥ 1.6.0. Supabase's own local-dev defaults turn email confirmations off ([supabase/cli config](https://github.com/supabase/cli/blob/develop/apps/cli-go/pkg/config/templates/config.toml)). The 4 GB minimum Supabase quotes is for the full stack ([Supabase docs](https://supabase.com/docs/guides/self-hosting/docker)). Nobody has published a footprint for a db+auth+rest+storage subset, so measure it before you size the host.

**Copy for the clone:** run one podman pod per project with db, auth, rest, storage and the Bun function server. Share a single edge proxy for routing and skip per-project gateways. Keep postgres-meta, or plain `pg_catalog`/`pg_policies` queries, behind a v0-style `get_backend_state` tool that returns table schema, RLS policies, function names and secret *names*. Every DDL statement becomes a migration shown in chat for approval, linted *before* apply, then applied, committed and followed by type regeneration. The linter fails on a public table with RLS disabled or a `USING (true)` policy for anon or authenticated. Secrets go into a write-only store the agent can list but never read. Scan the built bundle for service-role keys before publishing. Put a system-prompt rule in place so functions are generated as `export default { fetch }` rather than `Deno.serve`, instead of shimming Deno APIs.

## Design quality comes from token discipline and a token-free visual editor

Neither vendor publishes a design-quality eval. What they do publish shows design quality is enforced by rules and tooling, not by a smarter model. Lovable's leaked prompt requires semantic HSL tokens in `index.css` and `tailwind.config.ts` ("DO NOT use direct colors like text-white"), custom shadcn variants rather than overrides, and a special first-message routine. On the first message the agent writes down what the app should evoke, lists features, edits the design tokens first, "not hold back on design", and generates real images instead of placeholders ([leaked Agent Prompt](https://raw.githubusercontent.com/x1xhlol/system-prompts-and-models-of-ai-tools/main/Lovable/Agent%20Prompt.txt)). Leaked tools show image generation with flux.schnell for small images and flux.dev for hero images ([leaked tools](https://github.com/x1xhlol/system-prompts-and-models-of-ai-tools/tree/main/Lovable)). v0 gets inspiration from site inspection and screenshots plus generated image concepts ([Vercel](https://vercel.com/blog/v0-app)), and packages design systems as loadable skills ([Vercel](https://vercel.com/blog/introducing-the-new-v0-api)).

Both vendors built visual editors that skip the LLM entirely. Lovable's Visual Edits uses a custom Vite plugin that stamps "a unique, stable ID" on every JSX element at compile time. The project is kept as a Babel/SWC AST in the browser, and an edit modifies the AST, regenerates the file, diffs it, pushes it to the dev server and triggers HMR. A client-side Tailwind generator renders new classes optimistically. The stated motivation was that "AI is still (relatively) expensive" ([Lovable](https://lovable.dev/blog/visual-edits)). v0's Design Mode similarly "immediately updates the code without using any AI tokens" ([Vercel community](https://community.vercel.com/t/edit-ui-with-v0s-design-mode/17477)). On a local GPU, where tokens cost latency rather than money, this is an even bigger win: tweaking colors and padding should never queue behind a 30-second generation.

On evals, Lovable reports steps, tokens and turns per task on three benchmark families: 0-to-1 builds, iterative fixes and "verification discipline". It runs at least 3 runs per task at 95% confidence ([Lovable](https://lovable.dev/blog/opus-5-5-now-in-lovable)), and tracks stuck rate and publish rate in production ([Lovable](https://lovable.dev/blog/we-gave-our-agent-a-vent-tool)). v0 tracks error-free generation rate, meaning a working page rather than an error or blank screen ([Vercel](https://vercel.com/blog/how-we-made-v0-an-effective-coding-agent)). **Copy for the clone:** encode Lovable's token rules and first-message routine in the system prompt. Add a lint that rejects raw color classes. Ship the Vite `data-loc` plugin plus a Babel className editor before you tune any prompt. Build a small local eval harness of about 30 prompts across the three Lovable families, and score each on build success, blank-screen/console-error-free rendering (via Playwright), turns and tokens, with 3 runs each. Rerun it whenever the Qwen model or the harness changes.

## A component-by-component copy list

| Area | Copy from | What to build locally | Why |
|---|---|---|---|
| Model routing | Lovable | Big Qwen for builder; 7–14B for subagents, summaries, commits, stuck-judge; per-project replica affinity | Outcome per build, not per call, is the metric; prefix-cache hits |
| Agent state | Lovable | Append-only event log, inbox drained at iteration boundaries, Plan/Chat = write tools withheld | Resumable runs, mid-run messages, free forking |
| Context | v0 | Byte-stable system prompt; read-only `/docs` + example mount; inject tokens/router/recent files | Cache-friendly, no RAG infra |
| Edit tool | Lovable | Validated `line_replace` with ellipsis search, original line numbers; `write` for new files | Deterministic, low output tokens, fails loudly |
| Repair | v0 | Import/icon/dependency fixers, then `tsc` + Vite build fed back as tool results | Smaller models hallucinate more; pipeline beats model size |
| Runtime errors | v0 (next-lite) + Lovable | Injected console/error/fetch bridge + dev-server stdout; optional Playwright | v0 lost this bridge and its agent went blind |
| Sandbox | Vercel Sandbox | Rootless podman per project, stop on idle, FS persists, entrypoint relaunches Vite; proxy auto-starts | Same semantics, no snapshot machinery |
| Versions | v0 + Lovable | Commit per turn; restore = new commit; tags for bookmarks; redeploy functions | Linear, non-destructive history |
| DB restore | None (gap) | `pg_dump`/template copy on migration turns; opt-in "restore data" | Market-wide gap; cheap for you |
| Migrations | Lovable | SQL shown in chat, RLS lint pre-apply, commit to `supabase/migrations/`, regen types | CVE-2025-48757 prevention at the source |
| Backend introspection | v0 | `get_backend_state` tool: schema, RLS, functions, secret names | Stops agent trusting stale files |
| Secrets | Lovable | Write-only store, UI entry, paste detection | Agent never sees values |
| Functions | Supabase protocol | Bun on :9000 behind `/functions/v1`, JWT verify, CORS | supabase-js works unchanged |
| Visual edits | Lovable | Vite JSX ID plugin + Babel className edits + HMR | Zero-token tweaks; GPU time is scarce |

## Conclusion

The most useful finding is that the public record puts the moat in the deterministic layers, which are exactly the layers a self-hosted clone can reproduce at full fidelity. v0's composite model outscored raw Opus by about 15 points on error-free generation using streaming rewrites and sub-250 ms fixers. Lovable's biggest reliability gains came from giving the agent tools and feedback (logs, a knowledge base of fixes, a vent channel), not from a new model. A local Qwen stack will need these layers more than Sonnet ever did, so build them first and treat the model as the last variable to tune. The uncertainties that matter are the ones nobody publishes: loop termination and iteration caps, how Lovable picks its useful-context files, whether placeholder writes go through a fast-apply model, and the real memory footprint of a pruned Supabase subset. All four are cheap to settle empirically on your own hardware.

Two places let the clone beat the commercial products rather than just imitate them. Because every schema change passes through an approval gate you control, database snapshots tied to git commits make "restore everything" feasible where Lovable, v0 and Bolt all explicitly refuse. And because tokens on a LAN cost latency rather than dollars, token-free visual editing plus stopping idle containers matter more to how the product feels than any prompt improvement. The riskiest assumption in the target design is Bun as a drop-in edge runtime. It holds at the protocol level, but no one has published a production precedent, and JWT verification and per-function isolation become your own code to secure.
